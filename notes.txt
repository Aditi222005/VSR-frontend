## 4. Module 1 — User / Auth (Days 2–6)

### Backend (Person A)

**Entities & layers, in build order:**

1. `User` entity — `id, name, email (unique), password (hashed), role (USER/ADMIN), studyPreference (String, for recommendation later), createdAt`.
2. `UserRepository extends JpaRepository<User, Long>` with `findByEmail`.
3. `SecurityConfig` — `SecurityFilterChain` bean: permit `/api/auth/**`, secure everything else; disable CSRF (stateless API); configure CORS to allow `http://localhost:4200`.
4. `JwtUtil` — generate token (subject = email, expiry ~24h), validate token, extract claims. Use a library like `jjwt`.
5. `JwtAuthFilter extends OncePerRequestFilter` — reads `Authorization: Bearer <token>` header, validates, sets `SecurityContextHolder`.
6. `CustomUserDetailsService implements UserDetailsService` — loads user by email for Spring Security.
7. `AuthController`:
   - `POST /api/auth/register` → validate DTO, hash password with `BCryptPasswordEncoder`, save user, return success.
   - `POST /api/auth/login` → authenticate via `AuthenticationManager`, on success generate JWT, return `{ token, name, role }`.
8. DTOs: `RegisterRequest`, `LoginRequest`, `AuthResponse` — never return the `User` entity directly (don't leak the password hash).

**Order matters:** get registration fully working and testable in Postman *before* writing the JWT filter. Test flow: register → check row in DB with hashed password → login → get token → hit a dummy protected `/api/test/secure` endpoint with the token in Postman.

### Frontend (Person C)

1. `AuthService` (`src/app/services/auth.service.ts`) — `register()`, `login()` call the backend via `HttpClient`; on login success, store the JWT (in-memory service property + `localStorage` for persistence across refresh) and decode/store user role.
2. `environment.ts` — set `apiUrl: 'http://localhost:8080/api'`. Keep all HTTP calls pointed at this, not hardcoded URLs.
3. Components: `RegisterComponent`, `LoginComponent` — reactive forms (`FormBuilder`, `Validators.required`, `Validators.email`, min password length), call `AuthService`, show inline error messages from backend response.
4. `AuthGuard` (`CanActivateFn`) — blocks `/dashboard` and `/rooms` routes if no token.
5. `AuthInterceptor` (`HttpInterceptorFn`) — attaches `Authorization: Bearer <token>` to every outgoing request automatically. Register it in `app.config.ts` under `provideHttpClient(withInterceptors([authInterceptor]))`.
6. Routing (`app.routes.ts`): `/login`, `/register` public; `/dashboard`, `/rooms/:id`, `/profile` behind `AuthGuard`.

### How frontend and backend actually connect (this is the part that confuses beginners most)

- Backend runs on `localhost:8080`, frontend on `localhost:4200` — different origins, so **CORS must be configured on the backend** (`@CrossOrigin` or global config in `SecurityConfig`) or every call will fail silently with a CORS error in the browser console.
- Angular's `HttpClient` sends JSON; Spring's `@RestController` with `@RequestBody` deserializes it into your DTO automatically — just make sure field names match exactly (or use `@JsonProperty`).
- The token is **not a session** — Spring Security here is fully stateless. Every request must carry the JWT; there's no server-side "logged in" memory. This is why the interceptor is mandatory, not optional.
- Test the contract in Postman first, always. Once Postman gets a 200 with the right JSON shape, wiring Angular to it is just plumbing.

**Checkpoint (end of Day 6):** A user can register, log in from the Angular UI, get redirected to a dashboard, and refreshing the page keeps them logged in.

## 5. Module 2 — Public Rooms, statically seeded (Days 6–12)

This is your "admin panel" for now: **skip building real admin CRUD UI in this sprint.** Seed the 7–8 rooms directly via a data script. A real admin panel is Phase 2 work — building it now would eat days you don't have, for a feature only you will ever use before Aug 2.

### Backend (Person B)

1. `Room` entity — `id, name, description, category (e.g. "Coding", "Exam Prep", "Reading"), capacity, imageUrl, isPublic (boolean, default true)`.
2. `RoomParticipant` entity — `id, room (FK), user (FK), joinedAt` — tracks who's using which room (needed even before real-time features, for "X people currently studying here" counts and for recommendation history).
3. Seed data: create `src/main/resources/data.sql` with 7–8 `INSERT INTO room ...` rows, or a `CommandLineRunner` bean that inserts them on startup if the table is empty (safer — won't duplicate on restart). Pick categories that map to realistic `studyPreference` values from the User entity (e.g. "Coding", "UPSC/Exam Prep", "Reading", "Design", "General Focus").
4. `RoomController`:
   - `GET /api/rooms` → all public rooms.
   - `GET /api/rooms/{id}` → room detail.
   - `POST /api/rooms/{id}/join` → creates a `RoomParticipant` row (auth required — pull user from `SecurityContextHolder`).
5. `RoomRepository`, `RoomParticipantRepository`.

### Recommendation logic (Person B, once rooms are working)

Keep it rule-based — no ML needed for 30%, and it's honest to say so to your guide:

- Add `studyPreference` field to `User` (set during registration or profile edit).
- `GET /api/rooms/recommended` → simple query: rooms where `category = user.studyPreference`, sorted first; rest of the public rooms after. This is one `RoomRepository` method plus a small service-layer sort — not a separate "AI module." Be upfront in your report that this is milestone 1 of recommendation, and collaborative/ML-based recommendation is a stretch goal for later.

### Frontend (Person D)

1. `RoomService` — `getAllRooms()`, `getRecommendedRooms()`, `getRoomById()`, `joinRoom()`.
2. `DashboardComponent` — two sections: "Recommended for you" (from `/rooms/recommended`), then "All rooms" grid.
3. `RoomCardComponent` — name, category badge, participant count, "Join" button.
4. `RoomDetailComponent` — room description + join action + (placeholder for timer, to be built next phase).
5. `ProfileComponent` — lets the user set/edit `studyPreference` from a dropdown of the same categories used in seeded rooms, so the recommendation loop actually works end-to-end.

**Checkpoint (end of Day 12):** Logged-in user sees a dashboard with recommended rooms first (based on their profile), can browse all 7–8 rooms, and can join one.
